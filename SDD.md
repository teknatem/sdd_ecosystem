# Slice-Driven Design

Метод раскладки кода. Отвечает на вопрос **где что лежит и как это называется** —
и делает ответ проверяемым машиной.

SDD не заменяет DDD. DDD отвечает, *что* моделируем: агрегаты, границы, язык
домена. SDD отвечает, *как это лежит на диске*, чтобы модель можно было найти,
пересчитать и проверить, не читая код.

## Основная идея

**Индексированный срез ведёт дизайн.** Каждая сущность получает код вида
`<префикс><номер>_<имя>` (`a012_orders`, `p904_sales`, `u503_import`) и живёт в
одноимённых каталогах во всех крейтах сразу. Зная код, переходишь прямо в файл —
искать не нужно.

Из этого следует остальное:

- **Навигация без grep.** Код объекта — адрес. Каталог объектов генерируется из
  дерева исходников, поэтому не может разойтись с кодом.
- **Полнота проверяема.** Если у вида сущности объявлен набор ролей, отсутствие
  роли — вопрос, а не догадка.
- **Метрики осмысленны.** Срез — естественная единица измерения: связность,
  размер, покрытие документацией считаются по срезам, а не по случайным каталогам.

## Origins: тройка крейтов

Код одного объекта распределён по трём крейтам с фиксированными ролями. В отчётах
они сокращаются до одной буквы.

| Origin | Крейт | Что содержит |
|---|---|---|
| **B** | `backend` | Доступ к БД, бизнес-логика, проведение, серверные обработчики |
| **C** | `contracts` | DTO и метаданные, разделяемые между сервером и клиентом |
| **F** | `frontend` | UI объекта |

Имена крейтов — часть метода, а не бренда приложения, и не переименовываются под
продукт. Слои внутри крейтов зеркалят друг друга: `domain/a012_orders` существует в
том же виде во всех трёх.

Отсутствие origin у конкретного объекта — нормальная ситуация (служебная проекция
без UI), но она должна быть либо выведена из вида сущности, либо объявлена
отклонением. Незаявленная дыра — findings.

## Слои и их статус

Каталог первого уровня внутри `src/` — слой. У слоя есть статус, и он определяет,
какие вопросы к нему осмысленны.

| Статус | Что значит | Осмысленно спрашивать «полон ли набор ролей?» |
|---|---|---|
| `slice` | Зеркалируется по крейтам, элементы индексированы | да |
| `object` | Самостоятельная подсистема без индексов, живёт в одном-двух крейтах | нет |
| `shared` | Сквозной слой: не сущность, границы нет | нет |
| `removed` | Объявлен упразднённым. Файлы на диске — остатки, а не код | — |
| `ignored` | Явно вне модели | — |

Практический смысл различия именно в этом: инструмент, задающий вопрос о полноте
ролей сквозному слою, производит мусор.

## Индексы

Вид сущности задаётся формой индекса: префикс, число знаков, диапазон номеров.
Форма — это и правило именования каталога, и способ опознать вид по имени.

Типовые семейства (конкретный состав — дело приложения):

| Вид | Форма | Что это |
|---|---|---|
| Агрегат | `aNNN_` | доменная сущность или документ |
| Проекция | `p9NN_` | производная read-модель |
| Use-case | `uNNN_` | именованная операция (импорт, пересчёт) |
| Dashboard | `d4NN_` | готовый отчёт — потребитель слоя данных |
| Прочие | `dsNN_`, `dvNNN_`, `taskNNN_` | схемы, представления данных, задачи |

Два правила, которые легко нарушить:

- **Индекс без имени запрещён.** Каталог `dv001` вместо `dv001_sales_summary` —
  единственное семейство, где это когда-то допустили, и метаданные внутри всё
  равно несли полное имя.
- **Имя каталога обязано совпадать с идентификатором в собственных метаданных**,
  если сущность их имеет. Расхождение компилятор не ловит.

## Роли

Роль — это файл с закреплённым назначением внутри среза. Набор ролей объявляется
для пары «вид сущности × origin»:

- **`required`** — присутствует у 100 % срезов этого вида. Проверяется валидатором,
  разойтись молча не может.
- **`optional`** — присутствует у части. Доля фиксируется на дату замера и служит
  справкой, а не порогом.

Файл **вне обоих списков не является нарушением**. Доменный сервис, специфичный для
одного среза, — законный код, а не «файл не на месте». Инструмент, помечающий такое
как misplaced, ошибается.

Два принципа поверх набора:

**Одна роль — одно имя.** Если один и тот же слой доступа зовётся `api.rs` в одном
месте и `model.rs` в другом, это не стилистика: две трети навигации по проекту
строится на позиционном имени. Выведенное из употребления имя закрывается правилом
запрета, иначе оно вернётся первым же copy-paste и никто не заметит.

**Раскладка — не имя роли.** `foo.rs` и `foo/mod.rs` одинаково нормальны. Модуль
остаётся файлом, пока у него нет подмодулей, и становится каталогом, когда они
появляются. Исключение — позиционные каталоги, где имя несёт роль (`ui/list/`,
`ui/details/`): там форма каталога обязательна.

## Разделяемое ядро

Внутри слоя-среза может лежать каталог **без индекса** — общий код слоя. Имя одно:
`common`. Он **не является сущностью**: инструмент, посчитавший его агрегатом,
получает мусорные метрики и ложные findings.

Двух имён для одной вещи (`common` в одном крейте, `shared` в другом) быть не
должно — это фиксация разнобоя вместо его снятия.

## Хабы

Файл с искусственно высоким fan-in, который обязан трогать каждый срез: реестр
маршрутов, реестр страниц, реестр доступа. Любая метрика связности видит такой файл
как центр проекта и искажает показатели всех остальных.

Хабы перечисляются явно — не как индульгенция, а чтобы метрики оставались честными,
пока хаб не разобран.

## Отклонения

Раздел, отличающий **«ещё не сделали»** от **«так задумано»**. Без него и человек, и
инструмент обязаны считать любую дыру дефектом.

У каждого отклонения есть флаг намеренности:

- `intentional = true` — дашборд без серверной части, служебная проекция без UI.
  Findings по ним не производятся.
- `intentional = false` — незавершённый срез, файлы-сироты, не подключённые ни одним
  `mod`. Это долг с именем и адресом, а не тишина.

Отклонение с честным «не задумано» полезнее отсутствия записи: долг, у которого есть
строка в манифесте, не забывается.

## Почему манифест исполняется

Правила SDD жили прозой в трёх несинхронизированных документах, и каждый инструмент
держал их копию у себя. Разошлись все. Один из документов при разборе описывал
состав среза из файлов, которых **не существовало ни в одном срезе проекта** — он
годами выглядел авторитетно и был неправдой.

Отсюда два требования метода:

1. **Правила — в машиночитаемом файле** (`architecture.toml`, схема — в
   [MANIFEST_SCHEMA.md](MANIFEST_SCHEMA.md)), один на репозиторий, читаемый и людьми,
   и инструментами.
2. **Файл исполняется валидатором.** Стандарт, который никто не проверяет, дрейфует —
   и тогда он хуже отсутствия стандарта, потому что всё ещё выглядит авторитетно.

Отсюда же — разделение труда между документами:

| Документ | Отвечает | Как поддерживается |
|---|---|---|
| `architecture.toml` | какие правила действуют | правится руками, исполняется валидатором |
| `ARCHITECTURE.md` | какие объекты существуют и где | **генерируется** из дерева исходников |
| `llm.md` рядом с кодом | почему так и какие подвохи | пишется руками там, где домен неочевиден |
| `CONTEXT.md` | что означают термины домена | правится руками по мере разбора домена |

Перечня конкретных объектов в манифесте **нет намеренно**: список, введённый руками
в двух местах, разъезжается — ровно та ошибка, от которой уходим.

## Долг измеряется, а не запрещается

Метод не требует нулевого долга. Он требует, чтобы долг был **посчитан и не рос**:
у метрики есть направление и пороги, а храповик не даёт ей ухудшиться относительно
предыдущего состояния. Осознанный размен возможен явным флагом — с фиксацией того,
что размен состоялся.

Это дешевле запрета: линт на 500 существующих нарушений хоронит все остальные
диагностики, а храповик на ту же метрику работает с первого дня.
