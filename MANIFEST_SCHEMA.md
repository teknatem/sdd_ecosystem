# Схема манифеста `architecture.toml`

Манифест SDD — машиночитаемый стандарт **одного приложения**: один файл в корне
репозитория, который читают и люди, и инструменты. Здесь описано, из чего он
состоит; чем он является по смыслу — в [SDD.md](SDD.md).

Разделение обязанностей:

- **Этот файл** — схема: какие разделы бывают и что означают. Общий для метода.
- **`architecture.toml` приложения** — экземпляр: какие слои, индексы, роли,
  отклонения и правила действуют именно там.
- **Валидатор** — движок типов проверок. Конкретные правила живут в манифесте,
  поэтому новое правило заводится правкой TOML, а не правкой скрипта.

Чего в манифесте нет намеренно: **перечня конкретных объектов** (он генерируется в
каталог объектов) и **порогов метрик** (они живут рядом с семантикой метрик, где
объявлены направление, единицы и подписи).

---

## `[meta]`

Версия схемы и дата замера.

```toml
[meta]
schema_version = 2
measured_at = "2026-08-17"
measured_commit = "c3e73f1"
```

Числа в разделах ролей — не оценки, а результат подсчёта по коду на указанный
коммит. Дата нужна, чтобы расхождение читалось как «код уехал» или «файл устарел», а
не как «кто-то ошибся».

## `[layers]`

Статус каждого каталога первого уровня внутри `src/`.

```toml
[layers]
domain      = "slice"
quality     = "object"
shared      = "shared"
bi_timeline = "removed"
```

Допустимые значения: `slice`, `object`, `shared`, `removed`, `ignored` — смысл в
[SDD.md](SDD.md). Статус определяет, какие проверки к слою вообще применимы.

## `[indices]`

Форма индекса для каждого вида сущности.

```toml
[indices]
aggregate  = { prefix = "a", pattern = "a\\d{3}_", range = [1, 499] }
projection = { prefix = "p", pattern = "p9\\d{2}_", range = [900, 999] }
```

| Ключ | Смысл |
|---|---|
| `prefix` | буквенная приставка кода |
| `pattern` | регулярное выражение имени каталога |
| `range` | допустимый диапазон номеров, включительно |

`pattern` намеренно ограничен формой «литерал + группа цифр + литерал». Инструмент
разбирает его на части, а не тянет regex-движок; выражение сложнее этой формы —
ошибка, чтобы новый паттерн не оказался понят наполовину.

Ключ раздела (`aggregate`, `projection`, …) — это же имя используется в
`[roles.<вид>]`.

## `[roles.<вид>.<origin>]`

Набор ролей для пары «вид сущности × крейт».

```toml
[roles.aggregate.backend]
required = ["mod.rs", "repository.rs", "service.rs"]   # 43/43
optional = ["representation.rs", "posting.rs", "llm.md"]
# representation.rs 14/43 — нужен только тем, кто участвует в drilldown.
```

- `required` — есть у 100 % срезов вида; проверяется валидатором.
- `optional` — есть у части; доля пишется комментарием на дату замера, порогом не
  является.
- Файл вне обоих списков нарушением **не является**.

Комментарий с долей — обязательная часть записи, а не украшение: он объясняет, почему
роль опциональна, и не даёт превратить «нужна не всем» в «забыли у большинства».

### Под-роли

Позиционные части среза описываются вложенным разделом:

```toml
[roles.aggregate.frontend.details]
required = ["mod.rs"]
optional = ["api.rs", "view_model.rs", "page.rs", "tabs"]
```

В `optional` могут стоять и каталоги (`tabs`, `ui`), не только файлы.

## `[shared_kernel]`

Каталоги внутри слоя-среза, которые сущностями **не являются**.

```toml
[shared_kernel]
names = ["common"]
paths = ["crates/*/src/domain/common", "crates/*/src/usecases/common"]
```

Имя должно быть **одно**. Легализация двух имён для одной вещи фиксирует разнобой
вместо того, чтобы его снять.

## `[hubs]`

Файлы с искусственно высоким fan-in, искажающие метрики связности.

```toml
[hubs]
files = ["crates/backend/src/api/routes.rs"]
```

Каждая запись комментируется числом, объясняющим, почему файл здесь (сколько
маршрутов, импортов, срезов). Список — не индульгенция: он держит метрики честными,
пока хаб не разобран.

## `[thresholds]`

Пороги, относящиеся к **форме кода**, а не к метрикам качества.

```toml
[thresholds]
file_lines_warn = 1000
file_lines_hub  = 2000   # выше этого файл перестаёт быть большим и становится хабом
```

## `[conventions.<имя>]`

То, что инструменты ошибочно принимали за нарушение, с объяснением, почему это
норма. Раздел свободной формы: у каждой конвенции свои ключи, обязателен
разъясняющий комментарий.

Типовые случаи:

- **раскладка модуля** — `foo.rs` и `foo/mod.rs` равноправны (`both_forms_valid = true`);
- **формы URL** — единой формы нет осознанно, потому что URL это публичный контракт;
  указывается `preferred_for_new` для новых эндпоинтов;
- **регистр имён документов** — там, где имя файла является идентификатором *данных*,
  а не модуля, kebab-case является нормой и приводить его к snake_case нельзя.

Признак хорошей записи: она отвечает не «так сложилось», а «вот что сломается, если
привести к единой форме».

## `[deviations.<имя>]`

Осознанные отступления от собственных правил.

```toml
[deviations.frontend_only_dashboards]
what = ["d401_wb_finance", "d405_metadata_dashboard"]
why = "Дашборд — потребитель слоя данных. Бэкенд-часть нужна не всем."
intentional = true
```

| Ключ | Смысл |
|---|---|
| `what` | список объектов или путей |
| `why` | причина. Обязателен |
| `intentional` | `true` — так задумано, findings не производить; `false` — долг с адресом |

`intentional = false` — не признак незаполненного файла, а полезная запись: долг,
у которого есть имя, не забывается. Такие записи обычно подпираются метрикой,
удерживающей их число от роста.

## `[[rules]]` — правила валидатора

Массив таблиц. Валидатор реализует **типы** проверок; сами правила живут здесь.

### Общие поля

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | короткое имя, попадает в отчёт |
| `type` | да | тип проверки (ниже) |
| `severity` | да | `error` — считается гейтом; `warn` — только печатается |
| `scope` | обычно | glob каталогов, к которым правило применяется |
| `exempt` | нет | globs, которые правило пропускает молча |
| `waivers` | нет | список `{ path, why }` — точечные разрешения; `why` обязателен |

**`exempt` против `waivers`** — разница смысловая, и её нельзя стирать:
`exempt` = «правило сюда не относится по смыслу» (общее ядро не является срезом);
`waiver` = «относится, но мы осознанно разрешили вот здесь и вот почему».

Отключать правило, чтобы пройти проверку, нельзя. Waiver записывает причину —
удаление правила её теряет.

### Типы проверок

| `type` | Что проверяет | Свои поля |
|---|---|---|
| `required_files` | каждый каталог в `scope` содержит перечисленные файлы | `files` |
| `forbidden_filename` | выведенное из употребления имя не вернулось | `files`, `use_instead` |
| `dir_name_pattern` | имена каталогов в `scope` соответствуют выражению индекса | `pattern` |
| `dir_matches_metadata_id` | имя каталога равно полю `id` в его `metadata.json` | — |
| `snake_case_files` | имена `.rs`-файлов в snake_case | — |
| `embedded_doc_path_sync` | строковый путь к документу совпадает с соседним `include_str!` | `file`, `include_prefix` |

Последний тип стоит отдельного слова: это единственная проверка, ловящая то, чего
компилятор поймать не может. Когда путь к документу записан **дважды** — один раз в
`include_str!`, который проверяет компилятор, и один раз строкой, которую не
проверяет никто, — переименование каталога молча протухает: код продолжает работать,
но указывает на несуществующий исходник.

`forbidden_filename` заслуживает второго: правило существует не ради красоты, а
потому что после переименования старое имя возвращается первым же copy-paste со
старого среза, и без запрета этого никто не замечает.

### Заведение нового правила

1. Блок `[[rules]]` в манифест приложения.
2. Если нужного `type` нет — сначала тип в валидатор, потом правило в TOML.
3. Законное исключение оформляется `waivers` с причиной. Не удалением правила и не
   понижением `severity`.

## Как манифест попадает в метрики

Число нарушений уровня `error` — обычная метрика проекта: у неё есть направление и
пороги, и храповик не даёт ей расти. Прогонять валидатор нужно после переименований
и при заведении нового среза — то есть тогда, когда компилятор молчит, а структура
поменялась.
